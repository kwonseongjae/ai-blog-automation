# 기술 학습 블로그 운영

대상: https://jacks-aiblog.tistory.com/

작은 독립 예제를 실행하고 코드·실제 출력·공식 문서·한계를 묶어 기록한다. 한 편은 하나의 질문에 답한다. 익히지 않은 기술을 실무 경력으로 표현하거나 측정하지 않은 개선 수치를 쓰지 않는다.

## 원고 준비

등록된 실습과 설명은 `labs/learning_basics.py`와 `scripts/prepare_learning_posts.py`에 있다. 다음 명령은 실습을 실행하고 실제 출력과 코드를 원고에 넣는다.

```bash
python3 scripts/prepare_learning_posts.py
python3 -m unittest discover -s tests -v
```

원고·실습 변경을 검토하고 공개 저장소의 기본 브랜치에 반영한 뒤에만 발행할 수 있다. 실행 코드와 원고가 다르거나 공식 출처가 없으면 발행하지 않는다. 앞으로의 소재는 실제로 배운 내용과 해결한 문제에서 추가한다. 단순 정의 나열이나 다른 글의 요약으로 재고를 채우지 않는다.

## 발행 구성

- 한국 시각 매일 20:30에 하루 최대 한 편 실행한다.
- 기존 자동화의 암호화된 로그인 세션을 읽기만 한다. 로그인·추가 인증을 자동 시도하지 않는다.
- 기존 금융 발행기와 일정·이력·콘텐츠 처리 경로를 분리한다.
- 원고는 `docs/posts/catalogue.json` 순서로 고른다. 발행 후 원고 해시·날짜·URL을 기록한다.
- 글마다 공개 저장소의 고정 코드 버전과 테스트 링크를 덧붙인다.
- 발행 전 처리 중 상태를 저장한다. 결과가 불확실하면 다음 날도 자동 재발행하지 않는다.
- 재고가 없으면 보류한다. 근거 없는 새 글을 임의로 만들지 않는다.

환경 변수 `BLOG_AUTOMATION_ROOT`는 기존 자동화 프로젝트, `TECH_BLOG_STATE_DIR`는 새 블로그의 발행 상태 디렉터리를 가리킨다. 비밀 값은 공개 저장소에 넣지 않는다. 실행 환경에는 기존 세션 복호화에 쓰는 패키지와 Playwright 및 Chromium이 필요하다.

```bash
python3 -m automation.learning_blog --dry-run
systemctl --user status technical-blog.timer
systemctl --user status technical-blog.service
journalctl --user -u technical-blog.service -n 30
```

설치할 단위 파일은 `deploy/`에 있다. 이 PC와 사용자 서비스가 실행 중이고 네트워크·유효한 로그인 세션이 있어야 발행할 수 있다. 부팅 후 밀린 일정이 실행돼도 한국 날짜 기준의 중복 검사를 거친다.

## 실패 확인

`state.json`에 pending이 남아 있으면 먼저 실제 블로그와 관리 화면에서 같은 제목·내용의 글이 존재하는지 확인한다. 이미 발행된 글은 URL과 본문을 확인해 기록을 복구한다. 존재하지 않는 것이 확실할 때만 상태를 정리하고 재시도한다. 손상된 파일을 빈 상태로 자동 초기화하지 않는다.

`status.json`은 마지막 실행 결과, 상태 파일은 완료·확인 대기 원고를 담는다. 성공한 HTTP 응답만으로 발행 성공을 판단하지 않으며 공개 화면의 원고 식별자·제목·코드블록을 확인한다.

이미 발행된 글의 공개 본문을 재검증하고 기록을 복구할 때는 다음 명령을 사용한다.

```bash
python3 -m automation.learning_blog --confirm-url https://jacks-aiblog.tistory.com/글번호
```

관리 화면에서 같은 원고가 없음을 직접 확인했고 아직 공개 주소도 기록되지 않은 경우에만 다음 명령으로 확인 대기를 해제할 수 있다. URL이 있는 기록은 이 명령으로 지울 수 없다. 확인 복구한 날짜에도 새 글을 추가로 발행하지 않도록 처리한다.

```bash
python3 -m automation.learning_blog --clear-pending --confirmed-not-published
```

## 학습과 반응 평가

처음에는 학습 완성도와 재현성을 우선한다. 매주 실행 가능한 글, 본인이 설명할 수 있는 글, 정정이 필요했던 글과 준비 시간을 확인한다. 검색 관리도구를 연결한 뒤에는 색인·관련 검색어·노출·클릭을 함께 관찰한다. 8주를 첫 점검 시점으로 삼되 검색 성장이나 취업·수익을 보장하는 기간으로 해석하지 않는다.

GitHub의 실제 코드·문서 변경과 RSS 봇의 프로필 갱신은 구분한다. 예약 발행일에 맞춘 빈 커밋이나 날짜 조작을 하지 않는다. 경력 문장에는 확인된 직접 기여와 실제 결과만 사용한다.

## 화면 관리

화면 구성은 `automation/technical_skin.py`와 같은 이름의 CSS·JS 파일에 있다. Odyssey의 글·검색·카테고리·댓글 치환자는 보존한다. 상단 메뉴에서 전체 글·주제·공개 코드·RSS로 이동하며, 첫 실습은 1번 글로 연결한다. 모바일에서는 대문의 주제 버튼을 접고 상단 주제 메뉴와 본문 아래 카테고리를 이용한다.

사이드바 설정에는 소개·카테고리·최근 글만 배치한다. 글 수는 실제 카테고리 집계를 사용한다. 본문의 목차는 소제목이 세 개 이상일 때 접힌 상태로 표시하며, 코드 복사 권한이 없으면 코드를 선택해 직접 복사하도록 안내한다. 스킨을 수정하기 전에는 현재 HTML·CSS와 사이드바 설정을 비공개 운영 디렉터리에 백업한다.
