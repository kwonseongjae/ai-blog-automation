# 스킬이 안 불릴 때 점검하는 순서: 위치·파일 이름·머리글·설명·호출 설정을 하나씩 어겨 본 기록

같은 스킬을 아홉 가지 조건으로 바꿔 두 도구에 넣고 안 불리는 원인을 증상으로 가려내는 순서를 정리했습니다. 이름으로 불렀을 때 지정한 형식이 나와도 스킬로 등록되지 않은 경우가 있었습니다.

확인일: 2026-11-16 · 범위: Linux 한 환경, Codex CLI 0.167.2, Claude Code 2.1.325, 조건별 1회 실행, 대화형 화면의 스킬 목록은 확인하지 않음

## 스킬은 등록되고 선택되고 따라진다

점검에서는 등록 여부, 요청에 따른 선택, 본문 규칙 준수를 나눴습니다. 결과물의 형식은 이 가운데 규칙을 따랐는지만 보여 줍니다. 등록 여부까지 확인해 주지는 않습니다.

Claude Code 문서는 기대한 때 스킬이 쓰이지 않으면 다음 순서로 확인하도록 안내합니다.

1. 설명에 사용자가 자연스럽게 말할 키워드가 있는지 확인합니다.
2. `What skills are available?`에 스킬이 나타나는지 확인합니다.
3. 요청을 설명에 더 가깝게 바꿔 말합니다.
4. 사용자 호출이 가능하면 `/스킬이름`으로 직접 부릅니다.
5. 직접 호출도 인식되지 않으면 스킬 이름이 거부됐는지 확인합니다.
6. `paths`를 지정했다면 읽고 쓰는 파일이 현재 작업 폴더 안에 있는지 확인합니다.

프로젝트 위치는 `.claude/skills/<스킬 이름>/SKILL.md`, 개인 위치는 `~/.claude/skills/<스킬 이름>/SKILL.md`입니다. `name`을 생략하면 폴더 이름을 씁니다. 잘못된 머리글 YAML은 빈 메타데이터로 불러와 `/스킬이름`은 되지만 설명으로는 고를 수 없으며 오류는 `--debug`로 확인합니다. `disable-model-invocation: true`도 자동 선택을 막습니다.

목록에는 `description`과 `when_to_use`를 합쳐 1,536자까지만 표시합니다. 폴더 변경은 실행 중에도 감지하지만 세션 시작 때 없던 최상위 스킬 폴더를 만들었다면 `/reload-skills`가 필요합니다. 하위 폴더의 `.claude/skills`는 그 안의 파일을 처음 읽을 때 불러옵니다.

Codex 문서는 현재 작업 폴더부터 저장소 루트까지 각 폴더의 `.agents/skills`를 확인하며 `SKILL.md`에 `name`과 `description`을 요구합니다. 직접 호출은 `/skills` 또는 `$스킬이름`으로 합니다. 암묵적 선택은 `description`에 달려 있어 사용 범위와 경계를 짧게 쓰고 핵심 용도와 트리거 단어를 앞에 두도록 안내합니다.

`agents/openai.yaml`의 `policy.allow_implicit_invocation: false`는 요청만으로 선택되는 것을 막지만 `$스킬이름` 호출은 가능합니다. 변경은 자동 감지하며 반영되지 않으면 다시 시작하도록 안내합니다. 초기 목록은 컨텍스트 창의 2%를 넘지 않게 제한하므로 스킬이 많으면 설명부터 줄입니다.

## 정상 스킬 하나를 아홉 가지 조건으로 바꿔 봤다

앞선 입문 글의 `change-note`를 썼고 본문에는 변경 목록을 정리하는 규칙 세 개를 넣었습니다. 출력은 `- [분류] 내용` 줄과 마지막 `총 N건` 줄이며 정상 머리글에는 `name`과 `description`이 있습니다.

![정상 스킬에서 조건을 하나씩 바꿔 두 도구에 이름 호출과 이름 없는 요청을 보내 비교하는 순서](asset:flow)

조건마다 새 임시 폴더에서 아래 항목을 하나씩 바꿨습니다. 다른 도구의 스킬 위치에 넣는 경우도 포함했습니다.

| 조건 | 바꾼 내용 |
|---|---|
| 정상 | 정상 위치와 정상 `SKILL.md` |
| 위치 오류 | Codex는 `.claude/skills`, Claude Code는 `.agents/skills`에 둠 |
| 파일 이름 | `SKILL.md`를 `skill.md`로 바꿈 |
| description 없음 | 머리글에서 `description` 줄 삭제 |
| name 없음 | 머리글에서 `name` 줄 삭제 |
| 머리글 닫힘 없음 | 머리글을 닫는 `---` 삭제 |
| 설명이 다른 용도 | `description`을 회의록 용도로 바꿈 |
| 폴더 이름이 다름 | 폴더는 `release-tool`, `name`은 `change-note`로 둠 |
| 자동 호출 끔 | Codex는 `policy.allow_implicit_invocation: false`, Claude Code는 `disable-model-invocation: true` 설정 |

내용 차이가 선택에 영향을 주지 않도록 변경 목록을 고정하고 이름을 부르는 요청과 이름 없는 요청을 각각 보냈습니다.

> 로그인 화면에 비밀번호 보기 버튼 넣음 / 결제 오류 메시지 문구 고침 / 오래된 이미지 업로드 API 제거

| 요청 방식 | 입력 |
|---|---|
| Codex에서 이름으로 호출 | `$change-note <변경 목록>` |
| Claude Code에서 이름으로 호출 | `/change-note <변경 목록>` |
| 이름 없이 요청 | `릴리스 노트를 만들어줘. 변경: <변경 목록>` |

답변에 `총 3건`이 있고 `- [`로 시작하는 줄이 세 개 이상이면 형식을 따른 것으로 판정했습니다. 앞선 글에서 스킬 없이 받은 답은 제목과 설명 문장이 붙은 일반 릴리스 노트 형태였습니다.

Codex는 개인 설정이 섞이지 않도록 `CODEX_HOME`을 임시 폴더로 바꾸고 인증 파일만 링크했습니다.

```bash
codex exec --json -m gpt-6.1-sol -c model_reasoning_effort=low -s read-only
```

Claude Code는 아래 옵션으로 실행해 시작 정보와 도구 호출을 읽었습니다. 시작 정보에서는 스킬 목록과 슬래시 명령 목록을 구분했습니다.

```bash
claude -p --model haiku --setting-sources project,local --output-format stream-json --verbose
```

## Claude Code는 시작 정보의 목록으로 등록 여부를 볼 수 있다

시작 정보의 `skills`와 `slash_commands`에는 같은 스킬도 조건에 따라 한쪽에만 나타났습니다. 아래 표의 목록은 이 두 항목을 뜻합니다.

| 조건 | 시작 정보의 목록 | 이름으로 호출 | 이름 없이 요청 |
|---|---|---|---|
| 정상 | 두 목록 모두 | 형식 따름 | 형식 따름, `Skill` 호출 |
| 위치 오류 | 둘 다 없음 | Bash로 찾아 읽음, 형식 따름 | 형식 안 따름, 도구 호출 없음 |
| 파일 이름 `skill.md` | 둘 다 없음 | Bash로 찾아 읽음, 형식 따름 | 형식 안 따름 |
| description 없음 | `slash_commands`에만 | 형식 따름 | 형식 따름, `Skill` 호출 |
| name 없음 | 두 목록 모두, `change-note` | 형식 따름 | 형식 따름, `Skill` 호출 |
| 머리글 닫힘 없음 | `slash_commands`에만 | 형식 따름 | 형식 안 따름, 도구 호출 없음 |
| 설명이 다른 용도 | 두 목록 모두 | 형식 따름 | 형식 안 따름, 도구 호출 없음 |
| 폴더 이름이 다름 | 두 목록 모두, `release-tool` | `/change-note`에도 형식 따름 | 형식 따름, `release-tool`로 `Skill` 호출 |
| 자동 호출 끔 | 두 목록 모두 | 형식 따름 | 형식 안 따름, 도구 호출 없음 |

위치 오류와 파일 이름 조건은 두 목록에 없는데도 직접 호출한 답변이 형식을 따랐습니다. 답변 첫머리에서 해당 명령이 세션에 등록되지 않았다고 안내한 뒤 Bash로 폴더를 뒤져 파일을 읽었습니다.

머리글을 닫지 않은 조건은 슬래시 명령 목록에만 남았고 이름 없는 요청에는 반응하지 않았습니다. 문서의 빈 메타데이터 설명처럼 직접 호출과 설명에 따른 선택이 갈렸습니다.

`description`을 지운 조건은 이름 없는 요청에도 `Skill`이 호출됐고 `name`을 지운 조건은 폴더 이름으로 표시됐습니다. 문서는 `description`을 권장합니다.

폴더를 `release-tool`로 바꾼 조건은 목록과 실제 `Skill` 호출에 그 이름이 쓰였지만 `/change-note`를 입력한 답도 형식을 따랐습니다. 두 이름을 언제나 같은 방식으로 처리한다는 뜻은 아닙니다.

## Codex는 실행 기록으로 등록 여부를 짐작한다

Codex 출력에서는 등록 목록을 볼 수 없어 JSON 이벤트에 남은 명령을 확인했습니다. 정상 조건은 파일 검색 없이 곧바로 `cat .agents/skills/change-note/SKILL.md`를 실행했습니다.

표에서 ‘바로 읽음’은 이 실행 모양을 뜻하며 ‘찾은 뒤 읽음’은 `rg --files`, `find`, `ls` 같은 탐색 명령이 먼저 나온 경우입니다.

| 조건 | 이름으로 호출 | 이름 없이 요청 |
|---|---|---|
| 정상 | 바로 읽음, 형식 따름 | 바로 읽음, 형식 따름 |
| 위치 오류 | 찾은 뒤 `.claude/skills` 파일을 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |
| 파일 이름 `skill.md` | 찾은 뒤 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |
| description 없음 | 찾은 뒤 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |
| name 없음 | 바로 읽음, 형식 따름 | 바로 읽음, 형식 따름 |
| 머리글 닫힘 없음 | 찾은 뒤 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |
| 설명이 다른 용도 | 바로 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |
| 폴더 이름이 다름 | `release-tool` 경로를 바로 읽음, 형식 따름 | 바로 읽음, 형식 따름 |
| 자동 호출 끔 | 바로 읽음, 형식 따름 | 읽지 않음, 형식 안 따름 |

위치 오류 조건에서는 스킬을 찾겠다고 말한 뒤 `rg`로 `.claude/skills`의 파일을 찾아 읽었습니다. Codex가 스킬을 확인하는 위치가 아닌데도 답변 형식은 맞았습니다.

`description`이 없거나 머리글이 닫히지 않은 조건도 직접 호출에서는 파일을 찾아 읽었고 이름 없는 요청에서는 읽지 않았습니다. 정상 조건과 실행 모양이 달랐습니다.

문서는 `name`과 `description`을 요구하지만 `name`을 뺀 조건은 두 요청 모두 정상처럼 동작해 `description`을 뺀 조건과도 달랐습니다. 이를 근거로 `name`을 생략해도 된다고 일반화할 수는 없습니다.

설명을 회의록 용도로 바꾸거나 자동 호출을 끈 조건은 직접 호출할 때 바로 읽었고 이름 없는 요청에서는 읽지 않았습니다. 답변만 보면 같은 ‘자동으로 안 불림’이지만 위치 오류와는 실행 모양이 달랐습니다.

## 형식이 맞게 나와도 등록되지 않았을 수 있다

두 도구 모두 이름으로 부르면 폴더에서 파일을 직접 찾아 읽어 지정한 형식을 낼 수 있었습니다. 같은 조건에서 이름 없이 요청하면 따르지 않았으므로 이름 호출 성공만으로 등록을 확인할 수는 없습니다.

Claude Code는 시작 정보의 목록을 함께 보고 Codex는 파일을 찾는 명령 없이 바로 읽는지 비교합니다. 다만 Codex의 실행 모양은 등록 여부의 확정 증거가 아닙니다.

## 스킬이 안 불릴 때 확인하는 순서

이름 없는 요청이 실패한 조건은 여럿이었고 답변만으로는 위치 오류와 설명 문제를 구분하기 어려웠습니다. 다음 순서로 원인을 좁힙니다.

1. 증상: 이름으로 부르면 되는데 평소 요청에서는 안 됩니다. 원인 후보: 파일을 찾아 읽었을 수 있습니다. 확인: Claude Code는 시작 정보의 두 목록과 Bash 탐색 여부를, Codex는 파일 탐색 명령이 먼저 나왔는지를 실행 기록에서 보고 형식 준수는 따로 기록합니다.

2. 증상: 목록에 없거나 파일을 뒤져야 읽습니다. 원인 후보: 위치나 파일 이름에 문제가 있을 수 있습니다. 확인: 프로젝트 기준 Claude Code의 `.claude/skills/<스킬 이름>/SKILL.md`와 Codex의 `.agents/skills/<스킬 이름>/SKILL.md`를 대조하며 이번 `skill.md` 조건은 정상과 다르게 동작했습니다.

3. 증상: 직접 호출은 되는데 설명으로 고르지 못합니다. 원인 후보: 머리글 문제로, Claude Code에서 닫힘이 없을 때는 `slash_commands`에만 나타났고 이름 없는 요청에는 도구 호출이 없었습니다. 확인: 닫는 `---`와 YAML을 읽고 Claude Code 해석 오류는 문서가 안내한 `--debug`로 확인하며 Codex는 `name`과 `description`도 요구대로 갖춥니다.

4. 증상: 목록에 있거나 바로 읽을 수 있는데 자동 선택만 안 됩니다. 원인 후보: 설명의 용도가 다를 수 있으며 회의록 설명을 넣은 조건은 두 도구 모두 이름 없는 릴리스 노트 요청에서 형식을 따르지 않았습니다. 확인: 실제 요청과 설명을 맞춰 사용자가 말할 키워드가 있는지 읽고 Claude Code 문서가 안내한 요청 바꿔 말하기도 시도합니다.

5. 증상: 설명은 맞는데 이름 없는 요청에서 계속 빠집니다. 원인 후보: 자동 호출 설정이며 이번에도 직접 호출은 됐지만 이름 없는 요청은 형식을 따르지 않았습니다. 확인: 자동 선택을 막는 Claude Code의 `disable-model-invocation: true`와 Codex의 `policy.allow_implicit_invocation: false` 값을 읽습니다.

6. 증상: 수정 뒤에도 결과가 같습니다. 원인 후보: 변경 반영과 탐색 범위에 문제가 있을 수 있습니다. 확인: Claude Code의 새 최상위 스킬 폴더는 `/reload-skills` 필요 여부, 하위 폴더는 그 안의 파일 읽기 여부, `paths`는 현재 작업 폴더 안의 파일인지 확인하며 Codex는 자동 감지가 반영되지 않으면 다시 시작합니다.

`name`을 빼거나 폴더 이름을 바꾼 조건과 Claude Code의 `description` 없는 조건도 이름 없는 요청에서 형식을 따랐으므로 실패를 단정하지 않고 실제 표시된 이름과 읽은 경로를 확인했습니다.

## 이 실험으로 알 수 없는 것

각 조건은 Linux 한 환경에서 한 번씩 실행했으므로 반복 실행이나 다른 모델에서도 같은 결과가 나오는지는 알 수 없습니다. Windows와 macOS도 시험하지 않았습니다.

대화형 화면의 `/skills`와 `$` 목록은 확인하지 않았고 `What skills are available?` 질문도 보내지 않았습니다. 개인 위치와 같은 이름이 여러 위치에 있는 경우도 실험 범위 밖입니다.

설명이 1,536자나 컨텍스트 예산 때문에 잘리는 경우와 `paths` 지정은 문서에서만 읽었습니다. Codex의 등록 목록도 출력에서 확인하지 못했으므로 실행 기록의 차이를 등록 여부의 확정 증거로 쓸 수는 없습니다.
