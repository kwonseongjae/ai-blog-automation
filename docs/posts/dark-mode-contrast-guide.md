# 블로그에 다크 모드를 넣고 글자 대비를 재어 고친 기록: 낮은 대비 17곳을 3곳으로

다크 모드는 배경을 어둡게 바꾸는 데서 끝나지 않고 하드코딩된 글자색이 남으면 글을 읽기 어려워집니다. 공개 페이지 두 곳의 모든 글자 요소를 측정해 낮은 대비를 찾아 고쳤습니다. 수정 결과는 숫자로 남깁니다.

확인일: 2026-11-15 · 범위: 공개 페이지 2개(대문, 3번 글), Linux, 데스크톱 Chromium 145의 어두운·밝은 화면 설정 에뮬레이션, 실기기는 확인하지 않음

## 변수를 바꾸고 고정 색상을 따로 덮었다

![다크 모드를 적용하고 페이지의 글자 대비를 재어 낮은 곳을 고치는 순서](asset:flow)

코드를 읽어 보면 다크 규칙은 스킨 CSS의 `html[data-learning-theme=dark]` 선택자 아래에 모여 있고 먼저 CSS 변수 네 개를 바꿉니다. 글자와 링크, 선과 연한 배경에 쓰는 변수입니다.

변수만 바꿔서는 기존 CSS의 `#fff`, `#f1f4f9` 같은 고정 배경색이 남습니다. 대문 패널과 카드부터 표, 코드 상자와 메뉴까지 해당 선택자를 따로 덮었습니다.

티스토리가 본문 요소의 색을 `!important`로 정한 곳도 있어서 본문 제목과 목록, 강조와 목차 링크 일부에 `!important`를 썼습니다. 지저분한 선택이지만 이번에는 기존 색상을 덮는 데 필요했습니다.

화면 전환 버튼은 상단 메뉴와 떠 있는 버튼에 두었고 선택한 값은 `localStorage`에 저장합니다. 저장된 값이 없으면 기기의 `prefers-color-scheme` 설정을 따릅니다. 여기까지는 스크립트에서 확인한 내용입니다. 저장소 읽기와 쓰기는 `try/catch`로 감싸 저장소를 쓸 수 없는 환경에서도 화면 전환이 동작하도록 했습니다. 필요한 DOM 기능이 없으면 아무것도 하지 않습니다. 이 방어 동작은 노드 테스트로 확인했습니다.

## 글자 대비를 이렇게 쟀다

측정에는 Playwright의 데스크톱 Chromium 145를 썼고 화면 크기는 1280×900으로 맞췄습니다. 실제 공개 주소의 대문(`/`)과 3번 글(`/3`)을 열어 어두운 설정인 `color_scheme=dark`와 밝은 설정을 각각 에뮬레이션했습니다.

측정 대상은 글자가 직접 들어 있고 화면에 보이는 모든 요소입니다. 계산된 글자색과 가장 가까운 불투명 배경색을 사용했으며 대비 비율은 WCAG 상대 휘도 공식으로 계산합니다.

대비 비율이 3.5 미만이면 낮은 대비로 표시했으며 이 값은 이번 작업을 위해 제가 정한 기준입니다. WCAG의 일반 글자 AA 기준은 4.5이고 큰 글자는 3입니다. 따라서 3.5 이상 4.5 미만인 글자는 이번 표시에서 빠집니다. 낮은 대비 표시가 없어도 일반 글자 AA 기준을 충족한다고 볼 수는 없습니다. 아래 표는 이번 기준에 따른 결과이며 접근성 전체를 평가한 것은 아닙니다.

배경 이미지나 그라데이션 위의 글자는 계산에 한계가 있고 배경색이 투명하면 부모 요소의 색을 사용합니다. 실제로 글자 뒤에 보이는 색과 다를 수 있어 계산된 비율이 정확하지 않을 수 있습니다.

## 네 번 고치며 낮은 곳이 줄었다

각 차수마다 CSS를 고쳐 실제 블로그 스킨에 올렸고 적용 직후 같은 방법으로 다시 측정했습니다. 아래 숫자는 대비 비율이 3.5 미만으로 표시된 요소 수입니다.

| 적용 차수 | 어두운 화면 대문 | 어두운 화면 3번 글 |
|---|---:|---:|
| 1차(다크 규칙 처음 적용) | 4 | 17 |
| 2차 | 2 | 8 |
| 3차 | 2 | 4 |
| 4차(최종) | 1 | 3 |

어두운 화면의 대문은 4곳에서 1곳으로 줄었고 3번 글은 17곳에서 3곳으로 줄었습니다. 밝은 화면은 처음부터 끝까지 대문 0곳, 3번 글 4곳으로 같았습니다.

첫 측정에서는 본문 제목인 `h2`와 목록 글자가 검은색으로 남아 있었고 대비 비율은 1.17이었습니다. 배경은 바뀌었는데 글자색이 따라오지 않은 경우입니다. 변수 변경만으로 해결되지 않은 부분이 수치로 드러났습니다.

티스토리의 공감·공유·구독 문구는 짙은 회색인 `#333`으로 남아 대비가 1.42였으며 목차 링크의 기본 파란색은 3.27이었습니다. 본문 밖의 문구도 읽는 화면에 함께 놓이므로 측정 대상에 포함했습니다.

코드 복사 버튼은 흰 배경에 연한 파랑 글자여서 2.14였고 검색 버튼 글자는 2.31이었습니다. 오른쪽 사이드바의 분류 링크는 3.08입니다. 선택된 목록 페이지 번호도 흰 글자와 연한 파랑 배경의 조합으로 2.14가 나왔습니다.

해당 요소의 색상을 선택자별로 덮었고 기존 규칙을 덮어야 하는 일부에는 `!important`를 추가했습니다. 적용 후 같은 측정을 다시 돌리는 과정을 네 차수에 걸쳐 진행했습니다. 위 표는 그 결과입니다.

## 마지막에 남은 곳

최종 측정에서 3번 글에 남은 요소 중 두 개는 티스토리 기본 위젯이며 제가 만든 스타일은 아닙니다. 글 아래 구독 영역의 설명 링크인 `tt_desc`는 3.31입니다. 댓글 등록 버튼인 `tt-btn_register`는 1.26으로 나왔습니다.

두 요소는 밝은 화면에서도 똑같이 낮게 나왔고 댓글 등록 버튼의 흰 글자는 비활성 상태의 연한 회색 배경 위에 있었습니다. 최종 측정에도 이 수치가 남아 있어 낮은 대비가 일부 남은 상태입니다.

대문과 3번 글에는 관리 메뉴 아이콘용 숨은 글자 `ico_tistory_sign`도 남았으며 흰 배경에 흰 글자로 계산되어 1.0이 나왔습니다. 화면에서 읽는 글자는 아닙니다. 실제 읽기 문제와는 구분했지만 측정 기준에는 걸렸습니다.

밝은 화면의 3번 글에서는 코드 하이라이트의 `hljs-built_in`이 2.95였고 `hljs-string`은 2.96이었습니다. 이번에 만든 다크 규칙과 무관한 색상으로 두 요소는 수정 대상에서 제외했습니다.

## 다크 모드를 넣을 때 쓸 수 있는 기준

변수만 바꾸면 고정 색상이 남으므로 기존 CSS에서 고정 색상을 쓴 위치부터 찾습니다. 이번에도 CSS 변수를 바꾼 뒤 고정 색상이 남은 요소의 선택자를 따로 덮었습니다.

본문 글자뿐 아니라 검색 버튼, 사이드바 링크, 외부 위젯처럼 글자가 있는 모든 요소를 잽니다. 이번에도 검색 버튼과 사이드바 링크에서 낮은 대비가 나왔습니다.

숫자에 걸린 요소는 숨은 아이콘용 글자인지, 비활성 버튼인지 실제 역할과 상태를 확인합니다. 같은 낮은 수치라도 화면에서 맡는 역할은 다릅니다. 측정 기준 값도 결과와 함께 적어 둡니다.

## 이 측정으로 알 수 없는 것

스크린샷은 밝은 화면만 눈으로 확인했고 어두운 화면은 눈으로 보지 못했습니다. 어두운 화면에 대한 확인은 위 수치에 한정되며 읽는 사람이 실제로 편한지도 확인이 필요합니다.

실제 휴대폰과 Safari, 안드로이드에서는 확인하지 않았으며 분류 목록과 검색 결과, 모바일 보기도 이번 범위 밖입니다. 측정한 페이지는 대문과 3번 글뿐이므로 두 페이지의 결과를 블로그 전체로 넓혀 말할 수는 없습니다.

포커스 표시 색과 이미지 안의 글자는 확인하지 않았고 표지 이미지는 밝은 배경의 PNG 그대로 두었습니다. 이번 확인은 글자색과 배경색의 계산에 한정됩니다.

스크립트가 본문 맨 끝에서 실행되므로 어두운 설정의 기기에서도 처음 한순간 밝은 화면이 보일 가능성은 있습니다. 코드를 읽고 짚은 가능성이며 실제 발생 여부와 지속 시간은 이번 측정 범위 밖입니다.
