# 블로그 발행기가 잘못된 원고를 발행 전에 막는 방법: 규칙 13가지를 일부러 어겨 본 기록

발행기는 자동으로 글을 올리는 프로그램이고 잘못된 원고가 한 번 나가면 사람이 지우기 전까지 공개됩니다. 저는 발행 전에 원고를 막는 규칙을 코드에 두었습니다. 이번에는 규칙 13가지를 일부러 어겨 보고 어떤 메시지가 나오는지 확인합니다.

확인일: 2026-11-15 · 범위: 공개 저장소 kwonseongjae/ai-blog-automation의 검증 함수, 직접 만든 어긋난 원고 13건과 발행 주소 5건 실행, Linux 한 환경, 단위 테스트 50개

## 원고 하나를 발행 전에 세 단계로 거른다

코드를 읽어 보면 원고는 `docs/posts/catalogue.json`의 항목과 Markdown 파일로 구성되고 발행 전 검사는 세 단계로 나뉩니다. 항목에는 id, 제목, 분류, 출처 목록, 확인일, 확인 범위, 표지, 태그, 관련 글 등이 들어갑니다.

![원고 항목 검사, 저장소 반영 확인, 본문 길이 확인을 거쳐 발행하는 순서](asset:flow)

첫 단계는 `validate_article`의 항목 검사이고 각 값이 정해 둔 조건에 맞는지 확인합니다. id는 영문 소문자로 시작합니다. 나머지 문자도 영문 소문자·숫자·하이픈으로 제한합니다. 분류는 정해 둔 네 가지 중 하나입니다.

출처 주소는 https여야 하고 허용한 공식 문서 도메인이나 제 저장소 경로에 속해야 합니다. 안내 글에는 날짜 형식의 확인일과 확인 범위 문장이 필요합니다. 공식 출처 두 개 이상과 표지 이미지도 필수입니다.

태그는 비어 있지 않은 3~6개여야 하고 관련 글은 세 개 이하로 제한합니다. 원고 파일은 저장소 안에 있어야 합니다. 프로젝트 소개 항목이 있으면 주소가 제 GitHub 계정의 저장소인지 검사합니다. 이미지는 저장소 안에 있는 2MB 이하 PNG로 제한합니다.

두 번째 단계에서는 발행 직전 저장하지 않은 변경을 확인하고 원격 저장소 반영 상태를 검사합니다. 원고·실습·발행 코드에 저장하지 않은 변경이 있으면 멈춥니다. 현재 커밋이 원격 저장소의 main과 달라도 멈춥니다.

세 번째 단계에서는 본문이 700자 이상인지 확인하고 `## ` 소제목이 네 개 이상인지 셉니다. 여기까지는 코드를 읽어서 확인한 흐름입니다. 이번에 어긋난 원고를 넣어 실행한 대상은 첫 단계의 검증 함수입니다.

## 어긋난 원고 13건을 넣어 봤다

저는 스킬 입문 글의 항목을 복사하고 한 가지씩만 어긋나게 바꿔 `validate_article`에 넣었습니다. 원래 원고는 통과합니다. 바꾼 원고 13건에서 나온 메시지는 아래와 같습니다.

| 어긴 내용 | 발행기가 낸 메시지 |
|---|---|
| 공식 출처를 1개만 둠 | 안내 원고에는 확인 범위·공식 출처 두 개·표지가 필요합니다 |
| 허용 목록에 없는 출처 주소(example.com) | 허용된 공식 문서 주소가 아닙니다 |
| http 주소를 출처로 씀 | 허용된 공식 문서 주소가 아닙니다 |
| 표지 항목 삭제 | 안내 원고에는 확인 범위·공식 출처 두 개·표지가 필요합니다 |
| 확인일을 `2026/11/15`로 씀 | Invalid isoformat string: '2026/11/15' |
| 확인 범위를 빈 문장으로 둠 | 안내 원고에는 확인 범위·공식 출처 두 개·표지가 필요합니다 |
| 태그 2개 | 태그는 비어 있지 않은 3~6개가 필요합니다 |
| 태그 7개 | 태그는 비어 있지 않은 3~6개가 필요합니다 |
| 관련 글 4개 | 관련 글은 식별자 3개 이하의 목록이어야 합니다 |
| 없는 분류(잡담) | 허용되지 않은 카테고리입니다 |
| 원고 경로를 저장소 밖(`../../etc/hosts`)으로 지정 | 저장소 내부 원고가 필요합니다 |
| id에 대문자(`Skills`) | 원고 식별자가 올바르지 않습니다 |
| 프로젝트 주소를 다른 사람 저장소로 지정 | 프로젝트 주소는 본인 저장소여야 합니다 |

한 원고에 오류를 몰아넣지 않고 복사한 항목에서 매번 한 가지 조건만 바꿨습니다. 표의 각 행은 그 입력에서 나온 결과입니다. 이 결과만으로 다른 원고나 여러 오류가 섞인 경우까지 확인했다고 볼 수는 없습니다.

## 발행 주소도 같은 방식으로 막는다

발행 주소는 `validate_url`이 검사하고 대상 블로그의 공개 글 주소 형태만 통과시킵니다. https여야 합니다. 쿼리와 조각이 없어야 하며 경로는 `/` 뒤에 1 이상의 숫자가 오는 형태입니다.

주소 다섯 개를 함수에 넣었고 이번 실행에서는 아래 결과가 나왔습니다. 옛 블로그 주소와 관리 화면 주소도 포함합니다.

| 주소 | 결과 |
|---|---|
| https://jacks-aiblog.tistory.com/3 | 통과 |
| https://jacks-aiblog.tistory.com/3?x=1 | 대상 블로그의 공개 글 주소가 아닙니다 |
| https://jack-0314.tistory.com/3 (옛 블로그) | 같은 메시지 |
| http://jacks-aiblog.tistory.com/3 | 같은 메시지 |
| https://jacks-aiblog.tistory.com/manage (관리 화면) | 같은 메시지 |

첫 주소는 통과하고 나머지 네 주소는 모두 같은 문구로 거절됩니다. 이 표는 주소 검사의 결과입니다. 실제 글의 내용이나 공개 상태를 확인한 기록은 아닙니다.

## 실행해서 알게 된 약한 곳

날짜 형식 오류는 막혔지만 메시지는 사람이 읽기 어려운 파이썬 기본 문구로 나왔습니다. `Invalid isoformat string: '2026/11/15'`입니다. 규칙 대부분은 값을 확인한 뒤 `ValueError`를 내고 확인일에는 `date.fromisoformat`을 씁니다. 이번 실행에서는 이 함수의 기본 메시지가 그대로 나왔습니다. 날짜를 어떤 형식으로 고칠지는 적혀 있지 않습니다.

공식 출처를 하나만 둔 경우와 표지를 지운 경우, 확인 범위를 비운 경우는 원인이 다릅니다. 그런데 세 입력 모두 “안내 원고에는 확인 범위·공식 출처 두 개·표지가 필요합니다”라는 문구로 묶였습니다. 필요한 조건은 알 수 있어도 어느 항목을 고쳐야 하는지는 원고를 다시 봐야 합니다. 오류를 막는 것과 고칠 곳을 알려 주는 것은 별개였습니다.

## 이 방식을 내 자동화에 옮기려면

규칙마다 어긴 원고를 하나씩 만들어 넣어 봅니다. 통과하는 원고를 복사해 한 가지 조건만 바꾸면 입력과 메시지를 나란히 비교할 수 있습니다.

원고가 거절되는지만 보지 말고 메시지만 읽어도 원인을 구분할 수 있는지 확인합니다. 이번 기록에서는 서로 다른 원인이 같은 문구로 나왔습니다. 거절됐다는 사실만으로 메시지까지 충분하다고 보기는 어렵습니다.

코드에는 값으로 확인할 수 있는 조건만 둡니다. 사실 오류와 문장 품질은 사람이 읽어서 판단합니다. 이 발행기도 그렇게 나눠 두었습니다.

## 이 기록으로 알 수 없는 것

이번 실행은 Linux 한 환경에서 진행했고 저장소의 단위 테스트 50개도 모두 통과했습니다. 다만 저장하지 않은 변경과 원격 main 일치 여부는 어긋난 상태를 만들어 실행하지 않았습니다. 본문 700자와 소제목 네 개 조건도 이번에는 코드를 읽어서만 확인합니다.

원고 13건과 주소 5건의 결과는 확인했지만 모든 잘못된 원고를 막는다는 근거는 없습니다. 이미지 제한을 비롯해 이번 입력에 포함하지 않은 조건도 남아 있습니다. 검사를 통과한 원고의 사실과 문장 품질은 사람이 읽어서 판단합니다.
