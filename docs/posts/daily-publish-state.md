# 블로그 자동화에서 하루 한 번 발행을 지키는 방법

블로그 자동화에서 예약 작업이 끝났다는 로그만으로 글이 제대로 올라갔다고 말할 수 있을까요? 브라우저가 저장 버튼을 누른 뒤 멈추면 서버에는 글이 있고, 내 프로그램에는 실패만 남을 수도 있습니다. 이때 다시 실행하면 같은 글이 두 번 올라갑니다.

제가 만든 기술블로그 발행기에서는 날짜, 실행 잠금, 확인 대기 기록, 공개 본문 대조를 각각 사용합니다. 이 글은 공개된 구현과 테스트를 바탕으로 그 이유를 설명합니다.

## 날짜만 비교하면 부족하다

같은 날 이미 발행했는지 확인하면 평소의 중복은 줄일 수 있습니다. 하지만 두 프로세스가 동시에 시작하거나, 저장 직후 연결이 끊기는 경우는 날짜 하나로 처리하기 어렵습니다.

| 상황 | 날짜 확인만 했을 때 | 현재 구현의 처리 |
| --- | --- | --- |
| 같은 날 다시 실행 | 기존 기록이 있으면 차단 | 한국 날짜 기준으로 차단 |
| 두 실행이 동시에 시작 | 둘 다 미발행으로 볼 수 있음 | 파일 잠금으로 한 실행만 진행 |
| 저장 뒤 응답이 끊김 | 다음 실행에서 재발행할 수 있음 | 확인 대기 기록을 남기고 보류 |
| 본문 일부가 빠짐 | 저장 응답만 보면 성공처럼 보임 | 공개 글을 원고와 대조 |

예약 시간은 실행 시점을 정합니다. 하루 한 편이라는 규칙은 프로그램의 상태 기록과 검증이 지켜야 합니다.

## 발행 전에 진행 중이라는 기록을 남긴다

![글을 보내기 전에 확인 대기를 기록하고 공개 본문 검증 뒤 완료로 바꾸는 흐름](asset:flow)

핵심은 발행 버튼을 누르기 전에 `pending`을 저장하는 것입니다. 아래는 실제 코드의 처리 순서를 짧게 줄인 설명용 의사코드입니다. 그대로 실행하는 예제는 아닙니다.

```text
실행 잠금을 얻는다
확인 대기 기록이 있으면 멈춘다
오늘 완료한 글이 있으면 멈춘다
선택한 원고의 확인 대기 기록을 저장한다
글을 발행하고 공개 주소를 기록한다
공개 본문이 원고와 같은지 확인한다
검증이 끝난 경우에만 오늘의 완료 기록으로 옮긴다
```

공개 주소를 받았는데 검증이 실패한 경우에도 확인 대기는 남습니다. 프로그램이 모르는 사이에 올라간 글을 다시 만드는 일을 피하려는 선택입니다.

## 잠금과 파일 교체가 맡는 역할

실행 잠금은 두 프로세스가 동시에 발행 구간에 들어오는 것을 막습니다. 상태 파일은 임시 파일에 먼저 쓰고 파일 교체로 반영합니다. 두 장치는 해결하는 문제가 다릅니다.

| 장치 | 막으려는 문제 | 해결하지 못하는 것 |
| --- | --- | --- |
| 파일 잠금 | 같은 머신에서 겹친 실행 | 다른 머신의 독립 실행 |
| 임시 파일과 교체 | 쓰다 멈춘 상태 파일 | 외부 서버의 글 저장 실패 |
| 확인 대기 기록 | 결과를 모르는 작업의 재발행 | 기존 글의 자동 판별과 정정 |
| 원고 해시 | 같은 본문의 중복 등록 | 의미가 비슷한 서로 다른 글 |

현재 구성은 한 WSL 환경의 실행을 전제로 합니다. 여러 서버로 늘린다면 파일 잠금 대신 공유 저장소의 고유 키나 트랜잭션을 검토해야 합니다.

## 테스트에서 확인한 범위

공개 저장소의 테스트는 같은 한국 날짜에 두 번 호출해도 한 번만 발행되는지, 발행 중 예외가 나면 다음 날도 보류하는지, 잘못된 공개 주소와 본문 잘림을 성공으로 기록하지 않는지 확인합니다.

```bash
python3 -m unittest discover -s tests -v
```

이 검증은 상태 전이와 입력 경계를 확인하는 테스트입니다. 외부 서비스가 계속 동작한다는 보장이나 검색 노출·수익 개선의 증거는 아닙니다. 특히 저장 후 결과가 불명확하면 관리 화면에서 글을 확인하고 기록을 복구해야 합니다.

## 다른 자동화에는 어떻게 적용할까

영상 업로드나 알림 발송도 “보내기는 했는데 응답을 못 받은” 상황이 생길 수 있습니다. 작업을 시작한 기록과 성공이 확인된 기록을 나누고, 모호한 상태에서는 새로 보내기 전에 조회하는 원칙을 적용할 수 있습니다.

외부 서비스가 멱등 키를 제공하면 그 기능을 먼저 사용합니다. 제공하지 않으면 작업 식별자와 실제 결과를 대조할 방법이 필요합니다. 이 글의 파일 잠금 코드를 모든 서비스에 그대로 옮기기보다, 중복이 발생하는 경계를 먼저 찾는 편이 낫습니다.
