# 스킬(SKILL.md) 처음 만들기: Codex와 Claude Code에서 같은 파일로 써 본 결과

같은 `SKILL.md` 파일을 Codex와 Claude Code에 각각 넣고 릴리스 노트를 만들어 봤습니다. 이름으로 직접 부르는 경우와 이름 없이 요청하는 경우를 나눠 실행했습니다. 스킬이 없는 빈 폴더에도 같은 변경 목록을 넣어 결과를 비교했습니다.

확인일: 2026-11-15 · 범위: Linux 한 환경, Codex CLI 0.167.2, Claude Code 2.1.325, 조건별 1회 실행

## 스킬은 폴더 하나와 SKILL.md 하나다

공식 문서에 따르면 Codex의 스킬은 `SKILL.md` 파일이 들어 있는 폴더입니다. 필요한 경우 스크립트나 참고 자료를 함께 둘 수 있습니다. Claude Code의 `SKILL.md`도 지침이나 지식, 작업 절차를 담으며 관련 요청에서 자동으로 불러오거나 이름으로 직접 호출할 수 있습니다. 두 도구 모두 Agent Skills 공개 표준을 따릅니다. 이번에 만든 스킬은 변경 목록을 어떤 형식으로 정리할지 적어 둔 파일 하나로 끝납니다.

Codex는 `SKILL.md`에 `name`과 `description`을 필수로 요구합니다. Claude Code에서는 모든 frontmatter 필드가 선택이며 `description`을 권장합니다. 이번 파일에는 두 항목을 모두 넣었습니다. frontmatter는 파일 앞부분의 `---` 사이에 적는 설정입니다.

Codex는 처음부터 모든 스킬의 본문을 읽지 않습니다. 이름과 설명, 파일 경로를 목록으로 컨텍스트에 넣은 뒤 사용하기로 정한 스킬의 전문을 읽습니다. 문서에서는 이 방식을 점진적 공개(progressive disclosure)라고 부릅니다. Claude Code도 일반 세션에서는 설명을 컨텍스트에 넣고 전체 내용은 호출할 때 불러옵니다.

## 같은 파일을 두 도구에 넣어 봤다

만든 스킬의 이름은 `change-note`이며 변경 목록을 정해진 형식의 릴리스 노트로 바꾸는 용도입니다. 두 도구에 복사한 `SKILL.md` 전문은 같습니다.

```markdown
---
name: change-note
description: 변경 내용 목록을 한 줄씩 정리한 릴리스 노트로 바꾼다. 사용자가 변경 목록이나 커밋 목록을 주고 릴리스 노트, 변경 요약, 체인지로그를 요청할 때 사용한다.
---

변경 목록을 아래 규칙으로 정리한다.

1. 변경 하나를 한 줄로 쓰고 `- [분류] 내용` 형식을 쓴다. 분류는 추가, 수정, 삭제 중 하나다.
2. 마지막 줄에 `총 N건`을 쓴다.
3. 입력에 없는 내용은 추가하지 않는다.
```

공식 문서에 따르면 프로젝트용 위치와 사용자 전체에 적용되는 위치는 아래와 같습니다. Codex는 현재 작업 폴더부터 저장소 루트까지 각 폴더의 `.agents/skills`를 확인합니다. 관리자용 `/etc/codex/skills`와 내장 시스템 스킬도 지원합니다.

| 도구 | 프로젝트 위치 | 내 모든 프로젝트 위치 |
|---|---|---|
| Codex | `.agents/skills/change-note/SKILL.md` | `$HOME/.agents/skills/change-note/SKILL.md` |
| Claude Code | `.claude/skills/change-note/SKILL.md` | `~/.claude/skills/change-note/SKILL.md` |

이번 실행에서는 프로젝트용 경로만 사용했습니다. 작업한 곳은 Git 저장소가 아닌 임시 폴더입니다.

![스킬 폴더를 만들고 이름으로 부르거나 요청에 맞게 쓰이는지 확인하는 순서](asset:flow)

입력은 “로그인 화면에 비밀번호 보기 버튼 넣음 / 결제 오류 메시지 문구 고침 / 오래된 이미지 업로드 API 제거”로 통일했습니다. 아래 명령의 `<변경 목록>` 자리에 이 내용을 넣었으며 각 명령은 한 번씩 실행했습니다.

```bash
# Codex: 이름으로 호출 / 이름 없이 요청
codex exec -s read-only --skip-git-repo-check '$change-note <변경 목록>'
codex exec -s read-only --skip-git-repo-check "릴리스 노트를 만들어줘. 변경: <변경 목록>"

# Claude Code: 이름으로 호출 / 이름 없이 요청
claude -p "/change-note <변경 목록>" --setting-sources project,local
claude -p "릴리스 노트를 만들어줘. 변경: <변경 목록>" --setting-sources project,local
```

스킬이 없는 빈 폴더에서는 각 도구의 이름 없이 요청하는 명령만 실행했습니다. 스킬이 있는 경우와 비교한 결과는 아래와 같습니다.

| 조건 | Codex | Claude Code |
|---|---|---|
| 스킬 있음, 이름으로 호출 | `- [추가]`, `- [수정]`, `- [삭제]` 세 줄과 `총 3건` | 같은 형식 |
| 스킬 있음, 이름 없이 요청 | 같은 형식 | 같은 형식 |
| 스킬 없음 | 제목과 글머리표 세 줄. 입력에 없던 연동 확인 안내와 “확인하지 않은 사항” 문장을 덧붙임 | 새로운 기능·버그 수정·제거 소제목과 이모지 사용. 입력에 없던 마이그레이션 안내와 버전·날짜 요청을 덧붙임 |

스킬이 있을 때는 두 도구 모두 입력에 없는 내용을 덧붙이지 않았습니다. 세 번째 규칙인 “입력에 없는 내용은 추가하지 않는다”와 맞는 결과입니다. 이름을 생략한 요청에서도 지정한 형식이 나왔습니다.

스킬이 없는 경우 Codex는 “해당 API를 사용 중이라면 연동을 확인해 주세요”를 덧붙였습니다. Claude Code는 “최신 API로 마이그레이션해야 합니다”를 덧붙였습니다. 어느 쪽도 입력에 있던 내용은 아닙니다.

이번 실행에서 Codex가 표시한 사용량은 이름으로 호출했을 때 12,916토큰, 이름 없이 요청했을 때 13,136토큰이었습니다. 스킬이 없을 때는 10,187토큰으로 나왔습니다. 스킬 목록이 컨텍스트에 들어가는 영향일 수 있지만 이번 실행만으로 원인을 단정할 수 없습니다. Claude Code의 사용량은 기록하지 않았습니다.

## 이름으로 부르는 경우와 저절로 쓰이는 경우

공식 문서에 따르면 Codex에서는 `/skills`를 실행하거나 `$스킬이름`을 언급해 스킬을 명시적으로 호출합니다. 요청이 스킬의 `description`과 맞을 때도 스킬을 고릅니다. 설명에는 사용 범위와 경계를 짧고 분명하게 쓰라고 안내합니다. Claude Code에서는 `/스킬이름`으로 직접 부르며 관련 요청에서 자동으로 불러오기도 합니다.

이번 파일의 호출 이름은 각각 `$change-note`와 `/change-note`입니다. 실행해 보니 Codex의 `codex exec`에서 `$change-note`가 동작했습니다. Claude Code도 한 번 실행하는 `-p` 방식에서 `/change-note`를 사용할 수 있었습니다. 이번 확인은 두 도구의 한 번 실행 방식에 한정됩니다.

이름 없이 “릴리스 노트를 만들어줘”라고 요청해도 두 도구 모두 지정한 형식을 따랐습니다. `description`에 적은 사용 조건이 요청과 맞았기 때문으로 보입니다. 다만 설명만 바꿔 비교하는 실험은 하지 않았습니다.

Codex의 자동 호출은 스킬 폴더 안 `agents/openai.yaml`에 다음 설정을 넣어 끌 수 있습니다. 이때도 `$스킬이름`으로 직접 호출할 수 있습니다.

```yaml
policy:
  allow_implicit_invocation: false
```

Claude Code에서는 `SKILL.md`의 frontmatter에 다음 항목을 넣으면 도구가 스스로 호출할 수 없습니다. 사용자의 직접 호출은 가능합니다.

```yaml
disable-model-invocation: true
```

`user-invocable: false`는 반대로 사용자 호출을 막고 Claude만 호출하게 합니다. 기본값은 둘 다 호출 가능입니다.

## 처음 만든다면

Codex 문서의 안내처럼 한 스킬에 한 작업을 담고 명령형 단계와 입력·출력을 분명히 적습니다. 처음에는 반복해서 쓰는 작업 하나의 출력 형식부터 적어 보는 편이 좋습니다. 폴더에 `SKILL.md`를 직접 만들거나 내장 `$skill-creator`로 묻고 답하며 만들 수 있습니다.

`description`에는 작업 이름뿐 아니라 언제 쓰는지도 적습니다. Codex의 초기 스킬 목록 예산은 모델 컨텍스트 창의 2%이고 창 크기를 모르면 8,000자를 사용합니다. 스킬이 많아지면 설명부터 줄이므로 사용 조건을 짧고 분명하게 적습니다.

설명과 실제 요청이 맞는지 시험합니다. 이름으로 부르는 요청과 이름을 생략한 요청의 결과를 비교합니다. 스킬이 없는 빈 폴더에서도 같은 요청을 보내 출력 형식과 입력 밖의 문장이 붙는지 확인합니다.

파일 변경이나 배포처럼 되돌리기 어려운 작업은 직접 부를 때만 실행되도록 두는 편이 좋습니다. Claude Code 문서는 `/commit`, `/deploy`처럼 부작용이 있는 작업을 자동 호출 제한의 예로 듭니다. Codex에도 자동 호출을 끄는 설정이 있습니다.

## 이 실험으로 알 수 없는 것

이번에는 각 조건을 한 번만 실행했으며 같은 요청을 다시 보내면 결과가 달라질 수 있습니다. 규칙이 세 줄뿐인 단순한 예제라는 한계도 있습니다. 스크립트를 쓰는 스킬이나 큰 스킬은 확인하지 않았습니다.

같은 규칙을 스킬 없이 요청 문장에 직접 적은 경우와는 비교하지 않았습니다. 따라서 “스킬이 있어야만 이런 결과가 나온다”고 말할 수 없습니다. 확인한 것은 이번 파일을 넣은 조건에서 두 도구가 지정한 형식을 따랐다는 점입니다.

`description`과 맞지 않는 요청에서 스킬이 쓰이지 않는지는 시험하지 않았습니다. 이름이 같은 스킬이 여러 위치에 있을 때의 우선순위도 확인하지 않았습니다. 개인용 위치인 `~/.claude/skills`와 `$HOME/.agents/skills`는 직접 시험하지 않고 공식 문서 설명만 옮겼습니다.

Codex는 개인 전역 설정을 끄지 않았고 Claude Code는 `--setting-sources project,local`로 개인 설정을 제외했습니다. 두 도구의 실행 조건이 완전히 같지는 않습니다. 이 결과만으로 도구 간 성능이나 사용량의 우열을 판단할 근거는 없습니다.
