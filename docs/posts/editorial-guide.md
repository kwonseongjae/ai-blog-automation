# 기술 글 작성 기준

작성자: 권성재

## 한 편의 구성

독자가 겪는 질문 하나로 시작한다. 도입은 답과 적용 대상을 먼저 말한다. 비교할 선택지는 표로, 순서와 상태 변화는 흐름 그림으로 보여준다. 직접 실행했다면 입력·명령·실제 출력을 남기고, 설명용 의사코드와 아직 실행하지 않은 응용은 구분한다. 마지막에는 공식 출처와 확인 범위를 적는다.

설정법은 운영체제와 터미널을 먼저 구분한다. 처음 쓰는 사람에게 불필요한 확장 기능을 한꺼번에 설치시키지 않는다. 오류 해결 글은 증상·원인 후보·확인 방법·실제 수정·검증 순서로 쓴다.

## 입문 안내 글의 표준 구성

처음 쓰는 사람이 따라 할 수 있도록 아래 순서를 기본으로 한다. 모두 필수는 아니며, 해당 없는 항목은 뺀다.

1. 입력 위치 표시: 명령을 어디에 입력하는지(터미널, 도구의 입력창)를 문장 앞에 표시한다.
2. 준비물 확인: 필요한 것, 확인 방법, 없을 때 할 일을 표로 쓴다.
3. 단계와 걸리는 시간: 각 단계 제목에 예상 시간을 적는다. 직접 측정한 값만 쓴다.
4. 동작 확인: 성공했을 때 보이는 결과를 적는다.
5. 막힐 때: 증상과 확인할 것을 표로 쓴다.
6. 알아둘 한계: 실제로 확인하지 않은 환경과 범위를 적는다.
7. 확인 환경: 운영체제, 도구 버전, 확인일.
8. 더 읽을 글: 같은 분류의 다음 글과 공식 문서.

## 실제 프로젝트에서 이어갈 소재

| 프로젝트 | 글로 풀 질문 | 먼저 확보할 근거 |
| --- | --- | --- |
| 블로그 발행 | 응답을 못 받았는데 다시 발행해도 될까 | 상태 전이 코드와 실패 테스트 |
| 블로그 발행 | 로그인 세션은 어떻게 공유할까 | 비밀 값을 제외한 저장·갱신 흐름 |
| 블로그 화면 | 긴 표를 휴대폰에서 어떻게 읽을까 | 화면 크기별 실제 확인 |
| 견적 시스템 | 조건이 빠진 요청을 어떻게 처리할까 | 공개 가능한 입력 예시와 검증 코드 |
| 견적 시스템 | 부품 후보와 확정값은 어떻게 구분할까 | 공개 가능한 데이터 기준과 화면 |
| 영상 처리 | 업로드 직전 실패를 어떻게 복구할까 | 처리 단계와 재시도 경계 |
| 영상 처리 | 파일마다 처리 시간이 다른 이유는 무엇일까 | 같은 조건에서 측정한 실행 결과 |

다른 프로젝트의 소재는 조사 후보이며 구현·성과 확인을 마쳤다는 뜻은 아니다. 고객명·가격표·인증 정보·운영 데이터가 드러나는 화면과 로그는 공개하지 않는다. 공개 저장소 또는 새로 만든 작은 예제로 설명한다.

## 발행 전 확인

- 제목의 질문에 본문이 답하는가.
- 표나 그림이 설명의 반복을 줄이는가.
- 실행 결과와 예상 결과를 구분했는가.
- 실제 경험·수치·도구 버전의 근거가 있는가.
- 표지의 짧은 주제가 목록에서도 읽히는가.
- 휴대폰에서 본문이 넘치지 않고 표를 이동할 수 있는가.
- 원문·코드·공식 출처 링크를 확인했는가.
