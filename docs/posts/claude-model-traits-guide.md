# Claude Code 모델별 특징 비교: 같은 작업 세 가지를 haiku·sonnet·opus·fable로 두 번씩 돌린 기록

같은 작업 세 가지를 haiku·sonnet·opus·fable에 두 번씩 맡기고 결과를 비교했습니다. 순위는 매기지 않습니다. 턴 수와 표시된 비용을 비롯해 변경 범위와 보고 방식에서 차이가 난 부분만 기록합니다.

확인일: 2026-11-16 · 범위: Linux 한 환경, Claude Code 2.1.325, 별칭 haiku·sonnet·opus·fable의 기본 추론 강도, 작업 3가지를 각 2회, 작은 Python 프로젝트

## 별칭은 용도로 나뉜다

Claude Code 모델 설정 문서에서는 sonnet을 일상적인 코딩용으로 소개하고 opus를 복잡한 추론용으로 설명합니다. haiku는 단순한 작업을 빠르게 처리하는 용도입니다. fable은 가장 어렵고 오래 걸리는 작업용으로 소개돼 있습니다.

Anthropic API 기준으로 sonnet은 Sonnet 5.5를 가리키고 opus는 Opus 5.5에 대응합니다. haiku는 Haiku 5.5, fable은 Fable 5.2입니다. 별칭이 가리키는 버전은 시간이 지나면서 바뀝니다.

문서에 적힌 네 모델의 기본 추론 강도는 모두 `medium`이고 이번 실행에서는 강도를 따로 지정하지 않았습니다. 모델은 세션 중 `/model`이나 시작 명령의 `claude --model`로 고릅니다. Fable은 어떤 요금제에서도 기본 모델이 아니므로 직접 선택해야 합니다.

## 같은 작업 세 가지를 두 번씩 돌렸다

실행할 때마다 같은 시작 폴더를 새로 복사하고 모델 별칭만 바꿨습니다. 작업은 작은 Python 프로젝트로 준비합니다. 원인이 정해진 버그 수정과 파일 리뷰에 더해 개선 범위를 정하지 않은 요청도 넣었습니다.

| 작업 | 프로젝트와 시작 상태 | 확인할 결과 |
|---|---|---|
| 버그 수정 | `cart.py`, `pricing.py`, 테스트 4개. 처음에는 일부 실패 | 테스트 통과 여부와 테스트 파일 보존 |
| 리뷰 | `orders.py`의 함수 4개에 문제 4개를 넣음 | 문제 발견 여부와 번호 항목 수, 파일 변경 여부 |
| 모호한 요청 | `report.py`, 처음부터 통과하는 테스트 3개 | 변경된 줄과 파일, 테스트 결과, 되묻기 여부 |

버그 수정에는 다음 요청을 그대로 사용했습니다.

> 테스트가 실패합니다. 원인을 찾아 고치고 `python3 -m unittest discover -s tests` 로 통과를 확인해 주세요. 테스트 파일은 수정하지 마세요. 마지막에 무엇을 고쳤는지 두 줄로 알려주세요.

리뷰 요청은 다음과 같습니다.

> `orders.py`를 리뷰하고 발견한 문제를 번호 목록으로 알려 주세요. 파일은 수정하지 마세요.

모호한 요청에는 범위를 덧붙이지 않았습니다.

> `report.py`를 개선해 주세요.

실행 명령은 아래와 같고 `<요청 문장>`과 `<별칭>`을 작업별로 바꿨습니다.

```bash
claude -p "<요청 문장>" --model <별칭> --permission-mode acceptEdits \
  --allowedTools "Read" "Edit" "Write" "Bash(python3 -m unittest *)" \
  --output-format json --setting-sources project,local
```

버그 수정은 테스트 4개가 통과하는지 확인하고 테스트 파일의 해시도 비교했습니다. 리뷰는 답변에 문제별 키워드가 있는지 확인합니다. 번호 항목 수와 파일 변경 여부도 함께 기록했습니다.

모호한 요청은 변경된 줄 수와 건드린 파일을 비교하고 테스트 통과 여부와 되묻기도 확인했습니다. 아래 표의 값은 모두 `1회차 / 2회차` 순서입니다. 시간은 명령을 실행한 뒤 끝날 때까지 걸린 시간입니다.

턴과 비용은 실행 결과에 표시된 값을 옮겼으며 비용은 모델 단가나 요금제 가격을 뜻하지 않습니다. 표에서는 이를 ‘표시된 비용’으로 적습니다.

## 버그 수정은 모두 통과했고 턴 수와 비용이 달랐다

| 모델 | 시간(초) | 턴 | 표시된 비용(달러) | 변경된 줄 | 테스트 |
|---|---:|---:|---:|---:|---|
| haiku | 19.5 / 20.6 | 8 / 8 | 0.005 / 0.006 | 9 / 11 | 모두 4개 통과 |
| sonnet | 9.1 / 9.0 | 4 / 4 | 0.059 / 0.059 | 8 / 7 | 모두 4개 통과 |
| opus | 20.7 / 15.3 | 5 / 5 | 0.131 / 0.129 | 6 / 7 | 모두 4개 통과 |
| fable | 14.1 / 18.0 | 4 / 4 | 0.236 / 0.242 | 10 / 7 | 모두 4개 통과 |

여덟 번 모두 `cart.py`만 수정했고 `pricing.py`와 테스트 파일은 그대로였습니다. 테스트 파일의 해시도 같았습니다. 수정한 동작 역시 같습니다.

할인은 `eligible` 품목에만 적용하도록 고쳤고 배송비는 할인 후 금액을 기준으로 계산하게 바꿨습니다. 합계는 소수 둘째 자리로 반올림합니다. 변경된 줄 수에는 차이가 있어도 해결한 버그의 범위는 같았습니다.

haiku는 매번 8턴을 썼고 sonnet과 fable은 각각 4턴을 기록했습니다. opus는 5턴입니다. 표시된 비용은 haiku가 가장 작고 fable이 가장 컸습니다.

이 작업에서 sonnet의 실행 시간이 가장 짧았고 같은 모델 안에서도 실행 시간은 달라졌습니다. opus는 20.7초와 15.3초를 기록합니다. fable은 14.1초와 18.0초였습니다.

수정 뒤의 설명은 sonnet이 첫 줄에 내용을 묶어 한두 문장으로 적었고 opus와 fable은 1회차에서 번호가 붙은 두 항목을 썼습니다. 요청은 “두 줄로”였습니다. 같은 수정 결과라도 보고하는 모양은 달랐습니다.

## 리뷰는 모두 네 문제를 찾았고 항목을 나누는 방식이 달랐다

| 모델 | 찾은 문제(각 회차 4개 중) | 번호 항목 수 | 시간(초) | 표시된 비용(달러) |
|---|---:|---:|---:|---:|
| haiku | 4 / 4 | 9 / 10 | 13.1 / 14.6 | 0.004 / 0.004 |
| sonnet | 4 / 4 | 6 / 6 | 16.4 / 13.1 | 0.059 / 0.058 |
| opus | 4 / 4 | 6 / 5 | 19.1 / 17.1 | 0.111 / 0.111 |
| fable | 4 / 4 | 6 / 6 | 15.4 / 18.2 | 0.227 / 0.225 |

넣어 둔 문제는 페이지 번호 계산과 가변 기본 인자였고 금액의 `==` 비교와 빈 목록 평균도 포함했습니다. 네 모델 모두 이 네 문제를 찾았습니다. 여덟 번 모두 `orders.py`는 바뀌지 않았습니다.

차이는 번호 목록에서 드러났고 haiku의 1회차 답변은 아홉 항목으로 나뉘었습니다. `is_paid`에서는 초과 결제 처리와 키 누락을 별도로 적습니다. 부동소수점 비교도 독립된 항목이었습니다.

haiku는 `paginate`의 번호 계산 오류와 잘못된 입력을 나눴고 `average`의 빈 리스트와 `None` 값도 구분했습니다. 끝에는 타입 힌트와 docstring 부재를 사소한 항목으로 달았습니다. 한 함수에서 여러 지적이 나온 셈입니다.

1회차의 sonnet·opus·fable은 각각 여섯 항목을 적었고 추가로 짚은 내용에도 차이가 있었습니다. sonnet은 `add_tag`가 인자로 받은 `order`를 직접 바꾼다는 점을 적습니다. opus와 fable은 주문에 이미 있던 `tags`를 덮어쓴다는 점을 별도 항목으로 다뤘습니다.

haiku의 답변에는 이 덮어쓰기 항목이 없었고 줄 위치를 표시하는 방식도 모델마다 달랐습니다. opus와 fable은 `orders.py:3`처럼 줄 번호를 괄호로 달았습니다. sonnet은 `(4행 위)`, `(7행)`처럼 적습니다.

찾아낸 문제 수는 같았지만 번호 항목 수는 달랐고 이 숫자만으로 리뷰의 질을 판단할 수는 없습니다. 항목 수에는 문제를 나누는 방식도 반영됩니다.

## 모호한 요청에서는 변경 범위가 갈렸다

| 모델 | 변경된 줄 | 건드린 파일 | 시간(초) | 턴 | 표시된 비용(달러) |
|---|---:|---|---:|---:|---:|
| haiku | 52 / 32 | 1회차: `report.py`와 테스트 파일 / 2회차: `report.py` | 20.9 / 21.4 | 11 / 9 | 0.007 / 0.006 |
| sonnet | 19 / 19 | 두 번 모두 `report.py` | 16.2 / 10.9 | 6 / 6 | 0.067 / 0.063 |
| opus | 41 / 40 | 두 번 모두 `report.py`와 테스트 파일 | 27.1 / 29.1 | 9 / 8 | 0.164 / 0.167 |
| fable | 22 / 22 | 두 번 모두 `report.py` | 19.8 / 26.1 | 5 / 7 | 0.260 / 0.285 |

여덟 번 모두 되묻지 않고 수정을 진행했으며 실행 뒤 확인한 테스트는 모두 통과했습니다. 이 요청에는 테스트 파일 수정 금지가 없습니다. 테스트 파일을 바꾼 실행도 규칙 위반은 아닙니다.

1회차에서는 네 모델 모두 `top()`의 오류를 함께 고친다고 적었고 조건은 `n`이 행 수보다 클 때였습니다. 원래 이 경우에는 `IndexError`가 납니다. 처음부터 통과하던 테스트 3개만으로는 드러나지 않은 문제였습니다.

sonnet과 fable은 `report.py`의 두 함수를 f-string과 슬라이싱으로 바꾸고 docstring을 붙였습니다. opus는 여기에 타입 힌트를 더합니다. 테스트도 세 개 추가해 총 6개가 통과한다고 보고했습니다.

haiku도 타입 힌트와 모듈 설명을 더했고 테스트 파일에는 경계 조건 테스트를 추가했습니다. 1회차 변경은 52줄입니다. 2회차에는 테스트 파일을 건드리지 않았으며 변경은 32줄이었습니다.

sonnet과 fable은 답변에서 개선 범위가 정해져 있지 않아 동작을 유지하고 내부를 손봤다고 설명했습니다. 다만 `n` 초과 같은 새 동작에 테스트를 추가하지 않았거나 확인하지 않았다는 점도 적었습니다. 설명과 함께 확인 범위를 읽을 수 있었습니다.

fable은 `build_report`의 동작 변화도 별도로 알렸고 `name`이 문자열이 아니어도 문자열로 변환해 출력한다고 설명했습니다. 내부 수정이라는 보고와 함께 구체적인 변화도 적은 경우입니다.

haiku 1회차는 Python 실행이 승인 단계에서 막혀 테스트를 돌리지 못했다고 밝혔고 직접 실행해 확인해 달라고 적었습니다. 답변은 한국어 요청과 달리 영어였습니다. 2회차에는 한국어로 답했습니다.

실행 직후 같은 폴더에서 테스트를 다시 돌렸고 결과는 통과였습니다. 따라서 표의 통과 결과와 작업 중 테스트를 실행했다는 보고는 구분해서 읽습니다.

## 모델을 고를 때 쓸 수 있는 관찰

버그 수정에서는 네 모델이 같은 문제를 해결했고 차이는 턴 수와 표시된 비용 등에 나타났습니다. haiku는 8턴, sonnet과 fable은 4턴입니다.

리뷰에서는 네 문제를 찾았다는 결과가 같았고 답변을 읽는 데 필요한 정보의 모양이 달랐습니다. haiku는 항목을 더 잘게 나눴습니다. 줄 위치 표시는 sonnet·opus·fable의 답변에서 확인할 수 있었습니다.

모호한 요청에서는 sonnet과 fable이 `report.py`만 바꿨고 opus는 두 번 모두 테스트 파일까지 수정했습니다. haiku는 회차에 따라 달랐습니다. 수정할 파일 범위가 관심사라면 이 차이를 볼 수 있습니다.

보고 방식도 선택할 때 확인할 부분이고 테스트 실행 여부를 밝히는 문장은 결과를 해석하는 데 도움이 됐습니다. haiku 1회차는 실행하지 못했다고 알렸습니다. fable은 문자열 변환이라는 동작 변화를 따로 적었습니다.

이번 기록에서는 “어디까지 고쳤는가”와 “무엇을 확인했다고 말했는가”를 함께 읽었고 통과 여부만으로 답변을 묶지 않았습니다. 모델별 순위는 내리지 않습니다.

## 이 실험으로 알 수 없는 것

조건마다 두 번씩 실행한 기록이므로 시간과 비용 차이를 모델의 고정된 특성으로 단정하지 않습니다. 같은 모델에서도 시간이 달라졌습니다. 반복 횟수를 늘렸을 때 같은 차이가 유지되는지는 확인하지 않았습니다.

Linux의 작은 Python 프로젝트에서 실행했고 Windows·macOS나 더 큰 프로젝트는 확인하지 않았습니다. 여러 파일을 오가는 작업도 별도 검증 대상입니다. 추론 강도를 바꾼 경우 역시 이 기록에 없습니다.

리뷰에서 나온 지적의 타당성을 하나씩 전수 검증하지 않았고 번호 항목 수를 정확성 점수로 쓰지도 않습니다. 이번 글은 Claude Code만 다룹니다.
