# 입문자 중심 블로그 개편 설계

작성자: 권성재
기준일: 2026-11-15

## 목적

Jack의 AI 개발노트를 "AI를 처음 쓰는 개발자와 에이전트 입문자가 설정·선택·적용을 이해하는 블로그"로 정리한다. 독자는 고수가 아니라 입문자다. 동시에 블로그는 자기소개와 GitHub 프로젝트 소개의 입구 역할을 한다. 신뢰의 근거는 직접 한 프로젝트에 적용한 기록이다.

## 목표와 비목표

목표
- 글 흐름을 시작하기 → 도구·모델 비교 → 프로젝트 적용 순서로 재배치한다.
- 대문이 독자와 읽는 순서를 한눈에 보여준다.
- 각 적용 사례 글에서 GitHub 저장소와 본인 역할로 이어지게 한다.

비목표
- Python 실습 글 삭제. 파일과 이력은 보존하고 발행 순서에서만 뒤로 뺀다.
- 조회수·수익·취업 효과 약속. 측정 전에는 쓰지 않는다.
- 제품·모델 비교를 검증 없이 쓰는 것. 확인일과 공식 출처가 없는 비교는 발행하지 않는다.

실패 기준
- 이전 블로그처럼 발행 수만 늘고 읽히지 않는 상태.
- 근거 없는 장단점 서술, 비공개 프로젝트 정보 노출.

관리 카테고리는 아래 네 개로 한다. 이미 발행한 글 2편과 보류 실습은 마지막 분류로 옮긴다.

| 분류 | 역할 | 예 |
| --- | --- | --- |
| AI 시작하기 | 설치·로그인·지침 파일·스킬·권한 같은 첫 설정 | 터미널 코딩 도구 두 가지의 첫 설정 |

| Python·자동화 | 기존 Python 실습 | 한국 시간 기준, 실행 위치 |

## 발행 순서

정확한 제품명과 제목은 docs/posts/catalogue.json 기준이다. 이미 발행한 3편은 유지한다. 11월 15일 글은 발행 완료라 추가 발행하지 않는다. 아래는 11월 16일부터의 제안이며 새 글 제목은 가제다.

주의: 새로 쓸 글이 5편이다. 원고가 없는 날은 Python 글로 채우지 않고, 지금까지 진행한 프로젝트의 일부를 "어떤 AI로, 어떤 스킬과 기능을 써서 무엇을 만들고 어떻게 적용 중인가" 형식으로 쓴 프로젝트 적용 글로 채운다. 이 글도 같은 검증(확인일, 근거, 공개 가능 범위)을 거친다. 이 형식의 글이 없으면 발행기는 그날 보류한다.

## 대문

- 소개 문구를 독자가 보이는 문장으로 바꾼다. 예: "AI를 처음 쓰는 개발자를 위한 설정·비교·적용 기록".
- 소개 아래에 주제 칩 세 개(AI 시작하기 / 도구·모델 비교 / 프로젝트 적용기).
- "먼저 읽을 글" 2~3편을 직접 고른 입문 순서로 고정한다.
- 글 목록은 카드형으로 하고, 표지를 카드 안에 직접 그려 목록 썸네일이 비어 보이는 문제를 피한다.
- 코드·실행 결과 카드와 큰 배너는 쓰지 않는다.

## 자기소개와 GitHub 연동

- 적용 사례 글마다 "이 글의 프로젝트" 상자를 둔다: 프로젝트 이름, 저장소 또는 폴더의 고정 링크, 내가 한 일, 확인한 결과.
- 원고 목록에 선택 항목 project(이름·저장소 주소·역할)를 둔다. 값이 없으면 상자는 만들지 않는다.
- GitHub 프로필·저장소 README의 프로젝트 목록은 처음에는 수동으로 쓰고, 글이 쌓인 뒤 목록 항목에서 만드는 일을 검토한다.
- 공개 가능한 범위만 쓴다. 고객명·가격표·인증 정보·운영 데이터는 쓰지 않는다. 경력·성과는 확인한 것만 쓴다.

## 벤치마킹 반영과 나의 색

참고 대상(규니의 개발 블로그, 해당 GitHub 프로필)의 구조를 따르되 문장·이미지·도구는 복제하지 않는다. 2026-11-15에 두 곳과 우리 화면을 대조한 결과, 아래가 빠져 있어 추가한다.

블로그
- 글 하단 "관련 글": 원고 목록의 선택 항목 related(이미 발행한 글의 식별자 2~3개)로 만든다. 발행되지 않은 글은 링크하지 않는다.
- 사이드바 안내 상자 하나: 처음에는 입문 글 모음으로, 공개 프로젝트가 생기면 그 저장소로 바꾼다.
- 태그: 안내 글은 구체적인 태그 3~6개를 필수로 한다.
- 사이드바 인기글 탭은 이미 숨겨져 있다(공개 화면에서 확인). 데이터가 쌓이면 보이게 한다.
- 주제 허브 페이지: 벤치마킹 블로그의 "개발" 페이지처럼 티스토리 페이지 하나에 입문 글을 순서대로 모은다. 관리 화면에서 만든다.
- 입문 글 표준 구성(벤치마킹 저장소 README 참고): 입력 위치 표시, 준비물 확인, 단계마다 걸리는 시간, 동작 확인, 막힐 때 표, 알아둘 한계, 확인 환경, 더 읽을 글. 작성 기준 문서에 추가한다.
- 옛 블로그(jack-0314)에서 가져올 것: 글 첫머리의 읽는 시간 표시, 정정 안내 문구(선택 항목 correction), "이어서 보면 좋은 글"(관련 글과 같은 상자로 통합). 가져오지 않을 것: 시세 위젯·방문자 카운터(옛 블로그 일지에서 수집봇이 집계를 부풀린 것으로 확인), 광고.
- 보류: 입문 자주 묻는 질문 상자(글이 쌓인 뒤 재검토).
- 보류: 다크 모드 전환(벤치마킹 테마의 "테마" 메뉴), 3단 계층 카테고리(글 20편 전후에 재검토), 인기 글 위젯(조회 데이터 확보 후).

GitHub
- 프로필의 블로그 주소를 새 블로그로 바꾼다. 현재는 옛 금융 블로그를 가리킨다.
- 고정 저장소를 블로그와 관련된 것으로 교체한다. 지금은 이력서 하나뿐이다.
- 프로필 README에 About 블록과 바로가기 링크가 있는 대표 프로젝트 표를 추가하고, 기술 학습 소개문을 입문자 방향에 맞게 고친다. 로컬 사본이 실제 프로필보다 오래되어 먼저 맞춘다.
- 블로그 주제와 연결된 별도 공개 저장소는 지금 만들지 않는다. 공개 가능한 프로젝트가 정리된 뒤 결정한다.

나의 색
- 검증 기록: 모든 글에 실행 결과, 확인일, 고정 버전 코드 링크를 둔다.
- 실패·정정 공개: 옛 블로그에서 겪은 문제와 정정 이력을 프로젝트 적용 글의 재료로 쓴다.
- 수치가 있는 프로젝트 소개: 본인이 확인한 수치만, 공개 가능한 범위에서 대문과 프로필에 쓴다.

GitHub 계정 변경(주소 수정, 고정 저장소, README 반영)은 실제 계정에 반영되므로 각각 확인 후 진행한다.

## 제약
