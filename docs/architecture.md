# 안정화 설계 (Architecture)

> 설계 수준의 기록입니다. 구체 구현(특히 봇 탐지 대응)은 비공개이며, 코드 수준 상세는 [전자책](https://kwonseongjae.github.io/ebook-landing/)에서 다룹니다.

## 1. 발행은 왜 "그냥 자동화"가 아닌가

Tistory Open API 종료(2024-02) 이후, 발행은 순수 브라우저 자동화 문제가 되었습니다. 헤드리스 브라우저로 에디터(WYSIWYG)를 조작해 본문을 주입하고 발행 버튼을 누릅니다. 문제는 이 과정이 **상태(state)에 강하게 의존**한다는 것입니다 — 세션, 프로필, 봇 탐지, 타이밍. 상태가 어긋나면 멈춥니다.

## 2. 핵심 원칙: 버그 클래스를 없앤다

워치독·재시작 같은 복구는 증상을 옮길 뿐입니다. 같은 근본 원인이 다른 모습으로 되돌아옵니다. 그래서 **"그 실패가 일어날 수 없는 구조"**를 만드는 쪽으로 설계했습니다.

### 1회용 임시 프로필

공유 브라우저 프로필은 동시 접근 시 락 충돌(`Connection refused`)을 일으킵니다. 발행·삭제·편집마다 **새 임시 프로필을 만들고 끝나면 버립니다.** 공유 상태가 없으니 충돌이라는 버그 클래스 자체가 사라집니다. 로그인 상태는 프로필이 아니라 **별도 암호화 쿠키 저장소**에서 주입합니다.

### 세션 관리 (재로그인 회피)

재로그인은 2차 인증(2FA)을 유발해 자동화를 막습니다. 그래서 **재로그인을 하지 않는 것**이 목표입니다 — 쿠키를 주기적으로 갱신(keepalive)해 세션을 살아있게 유지하고, 만료 시엔 재로그인 대신 알림만 보냅니다.

### 멈춤 자가복구

브라우저 자동화는 특정 단계에서 무한 대기에 빠질 수 있습니다. 모든 발행 작업에 **하드 타임아웃**을 걸고, 초과 시 브라우저를 강제 종료한 뒤 재시도합니다. 종료 후 남는 락·소켓 잔여물까지 정리해 다음 시도가 깨끗한 상태에서 시작하게 합니다.

### 멱등 발행

한 번의 실패가 재시도로 중복 발행을 만드는 것을 막기 위해, **발행 직전에 "같은 글이 이미 있는가"를 확인**합니다(멱등 가드). 이로써 "정확히 한 번" 발행을 보장합니다.

## 3. 내구성 발행 큐

발행을 **enqueue(요청)와 worker(실행)로 분리**하고, 큐를 영속화합니다. 실패하면 **지수 백오프**(10분 → 30분 → 2시간 → 6시간)로 재시도하고, 한도를 넘으면 **dead-letter**로 격리합니다. 서버가 죽어도 큐가 디스크에 남아 재시작 후 이어집니다.

→ 동작하는 최소 구현 샘플: [`../samples/publish_queue.py`](../samples/publish_queue.py)

## 4. 운영 구조

- **스케줄링** — 수집/발행 잡을 분리해 시간대별로 실행
- **콘텐츠 다양성** — 같은 주제 연속 발행을 막아 검색 색인 중복 탈락 방지
- **색인 신청** — 발행 후 검색엔진에 색인 요청
- **모니터링** — 세션·발행·통계 상태를 점검하고 이상 시 알림

## 5. 배운 것

1. 자동화의 90%는 글 생성이 아니라 **"안 죽게 운영하는 것"**이다.
2. 땜빵은 버그를 옮길 뿐 — **버그 클래스를 없애는 설계**를 처음부터 한다.
3. 코드를 베끼면 플랫폼이 바뀔 때 깨진다 — **"왜 그렇게 설계했나"**를 이해해야 다시 만든다.
